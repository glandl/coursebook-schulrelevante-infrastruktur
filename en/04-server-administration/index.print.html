Server Roles: Windows and Linux

Sessions: 16.11.2026 and 23.11.2026 · Documentation technique: Runbooks · Role runbook due: 06.12.2026

A school network needs more than cables and addresses. Devices get their address automatically, names are resolved, teachers log in with one account on every computer, find their class folders, print, open the school website, and in summer 25 computer-lab PCs are set up again in one hour. Each of these tasks is a server role.

In this chapter you build, over two sessions, a working school network together out of eight server roles, and you build it twice:

  • in the Windows world with Windows Server 2025, the way many Austrian schools work, and
  • in the Linux world with Debian 13 and free software that does the same job without licence costs.

Each role team (two people, one team of three) takes one role and builds it in both worlds. How you split the work within the team is up to you. At the end, each team presents its role to the others and compares: what does each world do better, what does it cost, how dependent does it make the school on one vendor?

All machines run in the lecturer’s Proxmox lab. You do not need your own VM on the laptop, just a browser. See Access to the Proxmox lab.

Background reading

DHCP, DNS and VLANs are explained in chapter 3 (self-study). Read at least the sections on DHCP and DNS before you take on the DHCP, DNS or directory service role.

Subsections of Server Roles: Windows and Linux

Learning goals

After these two sessions you can:

  1. explain what a server role is, and describe each of the eight roles of a school network (DHCP, DNS, directory service, file shares, printing, web, client deployment, remote access) with an example from everyday school life,
  2. set up, test and undo one role in the Windows world (Windows Server 2025, preferably with PowerShell) and in the Linux world (Debian 13, free software),
  3. prove with acceptance tests from a test client that a role works from the users’ point of view,
  4. name the dependencies between the roles (no directory service without DNS, no domain accounts for shares, printers and remote access without a directory service) and narrow down faults along this chain,
  5. combine the Windows and Linux worlds (e.g. a Linux client on Active Directory, a Windows client on a Samba share) and explain which open protocols make this work (DHCP, DNS, LDAP, Kerberos, SMB, IPP, HTTP, PXE),
  6. compare both solutions of a role with reasons: licence costs, operating effort, vendor dependence, further development, data protection and suitability for support by a team of teachers,
  7. document your own work as a role runbook, with copyable commands and a column for undoing each step,
  8. explain your own role in a short presentation to others who did not build it themselves.

Snapshots: your way back

Each of your machines has the snapshot clean-start, the state before the first session. Create your own snapshot before every bigger step (Snapshots → Take Snapshot), e.g. before-dhcp-scope. If something goes wrong, you roll back with Rollback.

A snapshot is handy, but no substitute for the “undo” column in the runbook: at a school there is no simple rollback button for the production domain controller.

Lab rules

  1. Static addresses only from your range (see the IP plan in the chapter overview). A duplicate address knocks out another team’s machine.
  2. No additional DHCP server. In the lab VLAN only team 1’s Windows DHCP server and Kea hand out addresses, and only to the test clients. Many programs (e.g. FOG, Docker, dnsmasq) offer to start their own DHCP server: always decline.
  3. The lab router 10.50.13.254 is off limits. It is the gateway and DNS forwarder for everyone.
  4. No real personal data. User accounts are called e.g. lehrer01, schueler01, not like real people.
  5. Passwords for test accounts appear in the runbook only as placeholders (<password from password manager>), never in plain text in the portfolio.
  6. Windows evaluation: the Windows Server VMs run the evaluation edition (180 days from installation). It is meant for the lab, not for operation at a school.

Team 1: DHCP

Windows world: 10.50.13.10, Windows DHCP server · Linux world: 10.50.13.21, Kea DHCPv4 (Debian container)

The role at a school

On the first day of school, 25 students open their laptops and all of them are on the network immediately. Nobody types in an IP address. The DHCP server gives every device an address, subnet mask, gateway and DNS server, and remembers whom it “lent” what (lease). In real school networks every VLAN has its own range, and the router forwards the requests to a central server via DHCP relay (see chapter 3).

Dependencies

  • None for session 1. DHCP is the first role a device needs.
  • For session 2: the DNS servers of the domains (10.50.13.12, 10.50.13.23) must be running before you hand them out as a DHCP option.

Goal in the Windows world

  • The DHCP Server role is installed on 10.50.13.10.
  • A scope 10.50.13.100–10.50.13.119, subnet mask 255.255.255.0, lease time 8 hours.
  • Options: router 10.50.13.254, DNS server 10.50.13.254 (in session 2: 10.50.13.12).
  • A MAC filter (allow list): the server answers only the Windows test client. You get the MAC address from the lecturer.
  • Hint: PowerShell module DhcpServer; cmdlets start with Add-DhcpServerv4… and Set-DhcpServerv4….

Goal in the Linux world

  • The package kea-dhcp4-server is installed and the service is running.
  • A subnet 10.50.13.0/24 with a pool 10.50.13.120–10.50.13.139, same options as above (DNS in session 2: 10.50.13.23).
  • A client class that admits only the MAC address of the Linux test client. The pool is restricted to this class.
  • The configuration is in /etc/kea/kea-dhcp4.conf (JSON). Check before restarting: kea-dhcp4 -t /etc/kea/kea-dhcp4.conf.

Goal in session 2

  1. After the domain join, each server hands out the DNS server of its domain and the domain name (option 15).
  2. Windows: the DHCP server is authorized in Active Directory (otherwise it does not start in a domain).
  3. PXE for team 7: for team 7’s machines (reference machine and target machines, MAC addresses from team 7) you hand out options 66 (next server = 10.50.13.27) and 67 (boot file, depending on BIOS or UEFI; team 7 tells you which). Decide together whether Windows DHCP or Kea serves these machines.
  4. Combination: swap the MAC addresses in the two allow lists. Now the Windows test client gets its address from Kea and the Linux test client from Windows. Does the client notice a difference?

Pitfalls

Two DHCP servers in the same network

Windows DHCP and Kea both hear every DHCP request in the lab VLAN. Without an allow list, the faster one answers, and the client may get the wrong DNS server. Do not start a scope or pool without a MAC filter.

  • The server itself needs a static address; otherwise, in the worst case, it hands one out to itself.
  • Kea does not start if the JSON has a typo. Always check with -t first.
  • MAC addresses are written differently (BC-24-11-… on Windows, bc:24:11:… in Kea).
  • In Kea, the right network interface (eth0) must be listed in interfaces-config.

Entry points

  • Microsoft Learn: Deploy DHCP using Windows PowerShell
  • Microsoft Learn: DhcpServer module (PowerShell)
  • ISC: Kea Administrator Reference Manual, chapters The DHCPv4 Server and Client Classification
  • Debian: /usr/share/doc/kea-dhcp4-server/ and man kea-dhcp4

Comparison questions

  • How many lines of PowerShell versus how many lines of JSON? Which is easier to check and to keep under version control?
  • How do you back up the configuration and the leases, and how do you restore them?
  • What does the role cost (server licence, client access licences per device or user, CAL), what does Kea cost?
  • High availability: Windows has DHCP failover, Kea the high availability hook. How much effort is each?
  • What data does a DHCP server store about the students’ devices (MAC, host name, time), and for how long?

Team 2: DNS

Windows world: 10.50.13.11, Windows DNS server · Linux world: 10.50.13.22, BIND 9 (Debian container)

The role at a school

Teachers type moodle.schule.lan or drucker-lehrerzimmer, not 10.50.13.15. The DNS server translates names into addresses (and back) and forwards all other queries to the internet. Without DNS, almost nothing works at a Windows school: logging in to the domain finds the domain controller via DNS.

In the lab the work is split like this: the domain zones (win.schule.lan, linux.schule.lan) are created by team 3 when setting up the directory service. Your team builds the DNS around the domains: a zone with the names of all lab servers, the reverse lookup and the forwarders so that both worlds find each other.

Dependencies

  • None for session 1 (forwarding to the lab router 10.50.13.254).
  • For session 2: team 3’s domain controllers are running.

Goal in the Windows world

  • The DNS Server role is installed on 10.50.13.11, forwarder to 10.50.13.254.
  • A primary zone labor.test with an A record for every server of both worlds following the pattern win-<role> and lx-<role>, e.g. win-dhcp.labor.test → 10.50.13.10, lx-dhcp.labor.test → 10.50.13.21.
  • Zone transfer allowed only to 10.50.13.22.
  • Hint: PowerShell module DnsServer, e.g. Add-DnsServerPrimaryZone, Add-DnsServerResourceRecordA.

Goal in the Linux world

  • The package bind9 is installed; BIND works as a resolver for the lab (allow-recursion only for 10.50.13.0/24) with forwarding to 10.50.13.254.
  • A primary zone for reverse lookup 13.50.10.in-addr.arpa with PTR records for every server of both worlds.
  • Zone transfer allowed only to 10.50.13.11.
  • Check before every restart: named-checkconf and named-checkzone.

Goal in session 2

  1. Exchange across worlds: BIND becomes a secondary server for labor.test (transfer from 10.50.13.11), Windows becomes a secondary server for 13.50.10.in-addr.arpa (transfer from 10.50.13.22).
  2. Conditional forwarders together with team 3: whoever asks for linux.schule.lan ends up at 10.50.13.23, whoever asks for win.schule.lan at 10.50.13.12. And the domain controllers forward labor.test to you.
  3. Afterwards the Windows test client finds a Linux world server by name and vice versa.

Pitfalls

  • Serial number in the SOA record not increased: the secondary server does not pick up the change.
  • Forgotten dot at the end of a name in BIND zone files (ns.labor.test.): the name becomes ns.labor.test.labor.test.
  • An open resolver (allow-recursion any) answers queries from all over the world and can be abused for attacks.
  • On Debian 13, /etc/resolv.conf sets the DNS server directly, without systemd-resolved. Check changes on the server itself with dig @127.0.0.1.
  • .test is reserved for exercises (RFC 6761). At a real school, use a subdomain of your own registered domain (e.g. intern.ms-musterstadt.at), not .local.

Entry points

  • Microsoft Learn: DNS in Windows Server
  • Microsoft Learn: DnsServer module (PowerShell)
  • ISC: BIND 9 Administrator Reference Manual
  • Debian Wiki: Bind9
  • IETF: RFC 6761, Special-Use Domain Names

Comparison questions

  • Windows stores zones in a file or in Active Directory, BIND in text files. What does that mean for backup, version control (Git) and troubleshooting?
  • Which world reports configuration errors earlier?
  • What does a DNS server log about the students (which sites they visit)? Who at the school may see that?
  • Would it make sense to run DNS for the school at a provider on the internet? What speaks for it, what against?

Team 3: Directory service

Windows world: 10.50.13.12, Active Directory Domain Services (AD DS) · Linux world: 10.50.13.23, Samba as an Active Directory domain controller (Debian VM)

This team has three people because almost all other roles wait for you in session 2.

The role at a school

A teacher logs in with one account on the computer in the staff room, in the computer lab and on the projector PC. Her class folder is there everywhere, so is the printer, and when she leaves the school, the administration locks one account instead of twenty. That is what a directory service does: a central list of users, groups and devices, with login (Kerberos), queries (LDAP) and policies. In Austria, at many schools this is an Active Directory.

Dependencies

  • A static address and a final computer name before the setup. You do not rename a domain controller afterwards.
  • DNS: the domain controller itself becomes the DNS server of its domain. Forwarder to 10.50.13.254.
  • Time: Kerberos refuses login when the clocks differ by more than 5 minutes.

Goal in the Windows world

  • Computer name dc (fully dc.win.schule.lan), static address 10.50.13.12, DNS server 127.0.0.1.
  • AD DS role installed, new forest win.schule.lan, NetBIOS name WINSCHULE, DNS server integrated.
  • Organizational units Lehrende, Schueler, Gruppen, Geraete.
  • Test accounts lehrer01–lehrer03, schueler01–schueler05, groups GG-Lehrende, GG-Schueler.
  • Hint: Install-WindowsFeature AD-Domain-Services -IncludeManagementTools, then Install-ADDSForest. Accounts with New-ADOrganizationalUnit, New-ADUser, New-ADGroup.

Goal in the Linux world

  • The Debian VM is installed (the Debian 13 image is attached; minimal, without a desktop, with SSH server).
  • Computer name dc (fully dc.linux.schule.lan), static address 10.50.13.23, entry in /etc/hosts.
  • Samba as AD domain controller for linux.schule.lan, NetBIOS name LXSCHULE, Samba’s internal DNS server with forwarding to 10.50.13.254.
  • The same organizational units, accounts and groups as in the Windows world.
  • Hint: packages samba, krb5-user, winbind, smbclient. Set up with samba-tool domain provision, accounts with samba-tool user add, samba-tool group add, samba-tool ou add. The service is called samba-ad-dc; the services smbd, nmbd and winbind are disabled on a domain controller.
Why a VM and not a container?

Samba stores the permissions of the logon scripts and policies (sysvol) in extended file attributes and ACLs. In an unprivileged Linux container this often does not work or only partly. That is why the Linux domain controller runs as its own VM.

Goal in session 2

  1. The test clients join the domains: the Windows test client win.schule.lan, the Linux test client linux.schule.lan (with realm join, packages realmd and sssd).
  2. The servers of teams 4, 5 and 8 join the domain of their world so that shares, printers and remote access work with domain accounts. You support these teams.
  3. Combination: a second Linux machine (e.g. another team’s container) joins the Windows domain, or the Windows test client logs in to the Samba domain. Both work because Samba speaks the same protocols (LDAP, Kerberos, SMB).
  4. Conditional DNS forwarders together with team 2.

Pitfalls

  • Computer name or address changed after the setup: rebuild the domain (snapshot!).
  • The domain controller points with its DNS setting to itself, not to 10.50.13.254. Otherwise it does not find its own SRV records.
  • Samba: delete or rename /etc/samba/smb.conf before samba-tool domain provision, and replace /etc/krb5.conf with the generated file afterwards.
  • Samba: /etc/resolv.conf must point to 127.0.0.1 or its own address.
  • Avoid domain names ending in .local (collides with multicast DNS on Apple devices).
  • Password policy: test accounts need passwords that meet the default policy.

Entry points

  • Microsoft Learn: Install AD DS using PowerShell
  • Microsoft Learn: ActiveDirectory module (PowerShell)
  • Samba Wiki: Setting up Samba as an Active Directory Domain Controller
  • Samba Wiki: Distribution-specific Package Installation
  • Debian Wiki: AD Server with Samba

Comparison questions

  • Samba can do much of what Active Directory does, but not everything (e.g. parts of Group Policy, management only with the Windows tools RSAT or the command line). Which of it does a school really need?
  • What does a domain controller cost in each world: server licence, client access licences (CAL) for every teacher and every child?
  • How many people at a school can look after a Samba domain in an emergency, how many an Active Directory?
  • A directory service contains names, classes and login times of minors. Where is the data, who has access, who is responsible?
  • Microsoft increasingly promotes the cloud (Entra ID). What would the switch mean for your role?

Team 4: File shares

Windows world: 10.50.13.13, SMB shares with NTFS permissions · Linux world: 10.50.13.24, Samba (Debian container)

The role at a school

The class teacher puts worksheets into Klassen\3B; the students of 3B may read them but not delete them. Every teacher has a personal folder nobody else sees, and the administration has a drive that is invisible to teachers. These are shares (who gets to the folder over the network) and file permissions (who may do what inside it). The rules are written down in a permission matrix (see VLAN and permission matrices).

Dependencies

  • Session 1: none (local users and groups on the server).
  • Session 2: directory service (team 3) for domain accounts and groups.

Goal in the Windows world

  • File Server role (FS-FileServer) installed, folders under C:\Freigaben\….
  • Three shares according to the matrix, share permission generous, the actual rule in the NTFS permissions.
  • Access-based enumeration switched on: whoever has no access does not see the folder.
  • Session 1 with local groups GG-Lehrende, GG-Schueler and test accounts.
  • Hint: New-SmbShare -FolderEnumerationMode AccessBased, NTFS with icacls or Get-Acl/Set-Acl.

Goal in the Linux world

  • Package samba installed, three shares in /etc/samba/smb.conf according to the matrix.
  • Linux groups and users, Samba passwords with smbpasswd -a.
  • Invisibility: access based share enum = yes or hide unreadable = yes.
  • File permissions with owner, group and chmod; for the folder Austausch the sticky bit (chmod +t).
  • Check before every restart: testparm.

Goal in session 2

  1. Both servers join the domain of their world (Windows: Add-Computer; Samba: as a domain member with winbind, not as a domain controller).
  2. The permissions now apply to domain groups instead of local groups.
  3. Combination: the Windows test client maps the Samba share as a drive, the Linux test client the Windows share.

Pitfalls

  • On Windows, the stricter of share and NTFS permission always applies.
  • Inheritance: new subfolders inherit the permissions. Whoever disables inheritance has to set everything themselves.
  • Samba: Linux file permissions and Samba settings (valid users, read only) both apply.
  • SMB1 is insecure and switched off on both sides. Do not switch it back on, even if an old device asks for it.

Entry points

  • Microsoft Learn: SMB file sharing (overview)
  • Microsoft Learn: New-SmbShare, icacls
  • Samba Wiki: Setting up Samba as a Standalone Server, Setting up Samba as a Domain Member
  • Samba: man smb.conf

Team 7: Client deployment

FOG Project: 10.50.13.27 (Debian VM) · Windows reference machine: 10.50.13.16 · two empty target machines (VMs without an operating system)

The role at a school

End of August: 25 computers in the computer lab, carrying a school year’s worth of traces from 300 students. Instead of reinstalling each computer individually, you set up one computer cleanly (reference machine), take an image of it and play it over the network onto all the others at the same time. For this, the computers boot from the network (PXE), fetch a small boot program and write the image to their disk.

Why only one world here?

There is no Windows Server part for this role. The former Windows solution, Windows Deployment Services (WDS) with the Microsoft Deployment Toolkit (MDT), is no longer being developed by Microsoft. Microsoft relies on Windows Autopilot and Intune instead, i.e. on the cloud (see session 5). Check the current status in the sources.

FOG Project is free software, runs on Linux and deploys Windows and Linux images, even to a whole room at the same time (multicast). For your team, “both worlds” therefore means: one Windows image and one Linux image with the same free tool.

Dependencies

  • Session 1: none. You install the Debian VM and FOG.
  • Session 2: DHCP (team 1) has to give your machines the PXE options 66 and 67. Without that, no computer boots from the network.

Goal in session 1

  1. Debian VM installed (the Debian 13 image is attached; minimal, without a desktop, with SSH server), static address 10.50.13.27, computer name fog.
  2. FOG Project installed (current stable version from the official repository, installer script installfog.sh).
  3. Web interface http://10.50.13.27/fog/ reachable (from the Windows test client), default password changed.
  4. Two image definitions created: win-referenz (Windows) and debian-referenz (Linux).
  5. MAC addresses of your three machines (reference machine, two target machines) noted and given to team 1. Find out in Proxmox whether the machines boot with BIOS (SeaBIOS) or UEFI (OVMF).
FOG must not start its own DHCP server

The installer script asks whether FOG should take over DHCP. The answer is no (also for the questions about DHCP router and DNS). There are already two DHCP servers from team 1 in the lab VLAN. A third one would give all teams wrong addresses.

Goal in session 2

  1. With team 1: the target machines and the reference machine get next-server 10.50.13.27 and the matching boot file via DHCP (undionly.kpxe for BIOS, ipxe.efi for UEFI).
  2. Linux image: install a minimal Debian on target machine 1, capture it as debian-referenz (capture), deploy it to target machine 2 (deploy).
  3. Windows image: capture the reference machine .16 as win-referenz and deploy it to a target machine.
  4. Optional: multicast to both target machines at the same time.

BIND and DNSSEC

By default, BIND validates answers with DNSSEC. The endings .lan and .test do not exist on the internet, and the root servers can prove that. BIND therefore discards the domain controllers’ answers and reports SERVFAIL. Fix in named.conf.options: validate-except { "lan"; "test"; };. At a real school with a registered domain (e.g. intern.ms-musterstadt.at) the problem does not occur.

If logging in to the domain does not work

Troubleshoot in this order; it solves most cases:

  1. Network: ping 10.50.13.12 or 10.50.13.23.
  2. The client’s DNS server: does it point to the domain controller? (ipconfig /all, cat /etc/resolv.conf)
  3. SRV record: Resolve-DnsName _ldap._tcp.<domain> -Type SRV or host -t SRV _ldap._tcp.<domain>.
  4. Time: if client and DC differ by more than 5 minutes, Kerberos fails with an unhelpful message.
  5. Account and password: upper-case realm with kinit (lehrer01@LINUX.SCHULE.LAN).
  6. Only then: the domain controller’s logs (Event Viewer Directory Service or journalctl -u samba-ad-dc).

Demo: certificate services

When: 23.11.2026, approx. 15 min within the 10:30–11:15 block · Who: lecturer (demonstration), for everyone to read afterwards · Machines: 10.50.13.18 (Windows), 10.50.13.29 (Linux)

Demonstration, not a team task

Certificate services are not a team’s role. Your own certificate authority is hard to undo (see below) and depends on the directory service. That is why the lecturer shows it once in each world.

Status: untested

The commands have not yet been run in the Proxmox lab. Tested on: open.

What it is about

Team 6’s websites run with HTTPS, but with self-signed certificates. The browser warns, and rightly so: it cannot check whether it is really talking to the school server. Public authorities such as Let’s Encrypt do not issue certificates for internal names like intranet-win.labor.test.

The solution is the school’s own certificate authority (CA):

  1. The CA creates a root certificate and keeps its private key secret.
  2. All school devices trust this root certificate.
  3. The CA issues certificates for internal servers. Because the devices trust the CA, they also trust these certificates: no more warning.

What a school needs its own CA for

UseWhat the certificate provides
Internal websites (intranet, Moodle, printer interfaces)HTTPS without browser warning
Wi-Fi with 802.1X (EAP-TLS)teachers’ devices log in with a certificate instead of a shared Wi-Fi password and automatically end up in the right VLAN (see chapter 3)
Device management (session 5)Intune and other MDM systems distribute device certificates (SCEP, PKCS)
Directory serviceencrypted LDAP connections (LDAPS) between servers

Part 1: Windows world with AD CS (approx. 7 min)

Prerequisite: 10.50.13.18 is a member of win.schule.lan. An enterprise CA needs Active Directory: it publishes its root certificate there, and all domain members trust it automatically.

# on 10.50.13.18, as domain administrator
Install-WindowsFeature ADCS-Cert-Authority -IncludeManagementTools
Install-AdcsCertificationAuthority -CAType EnterpriseRootCa `
    -CACommonName "Schule Musterstadt Root CA" `
    -KeyLength 4096 -HashAlgorithmName SHA256 `
    -ValidityPeriod Years -ValidityPeriodUnits 10

Issue a certificate for team 6’s website and bind it in IIS:

# on 10.50.13.15 (IIS), as domain administrator
$cert = Get-Certificate -Template WebServer `
    -DnsName intranet-win.labor.test `
    -CertStoreLocation Cert:\LocalMachine\My
$thumb = $cert.Certificate.Thumbprint
# remove team 6's existing HTTPS binding, then bind again
# ("intranet" = name of the site that team 6 chose)
New-IISSiteBinding -Name "intranet" -Protocol https `
    -BindingInformation "*:443:intranet-win.labor.test" -SslFlag Sni `
    -CertificateThumbPrint $thumb -CertStoreLocation "Cert:\LocalMachine\My"

Show:

  1. On the Windows test client run gpupdate /force, then show the new CA in certlm.msc under Trusted Root Certification Authorities.
  2. In the browser, https://intranet-win.labor.test: no warning, padlock, certificate chain up to the school CA.
  3. Counter-check on the Linux test client: the warning remains. It is not in the Windows domain and does not know the CA.

Part 2: Linux world with step-ca (approx. 5 min)

step-ca by Smallstep is a free certificate authority. Install it beforehand on 10.50.13.29 following the official instructions (Debian packages step-cli and step-ca). Team 2 adds ca.labor.test → 10.50.13.29 to the zone labor.test.

# on 10.50.13.29: set up the CA (once, beforehand)
step ca init --name "Schule Musterstadt Linux CA" \
    --dns ca.labor.test --address :443 --provisioner admin
step-ca $(step path)/config/ca.json      # start the CA (in the foreground for the demo)

# issue a certificate for team 6's nginx site
step ca certificate intranet-lx.labor.test intranet-lx.crt intranet-lx.key

Copy certificate and key to 10.50.13.26 and enter them in nginx as ssl_certificate and ssl_certificate_key, then nginx -t, systemctl reload nginx.

Make the Linux test client trust the CA:

# the root certificate is on 10.50.13.29 under $(step path)/certs/root_ca.crt;
# copy it to the test client and add it system-wide
sudo cp root_ca.crt /usr/local/share/ca-certificates/schule-linux-ca.crt
sudo update-ca-certificates
curl https://intranet-lx.labor.test     # without -k, without warning

Show:

  1. curl works without -k.
  2. Validity: step certificate inspect intranet-lx.crt shows that the certificate is valid for only 24 hours (step-ca default). Short-lived certificates are more secure but have to be renewed automatically, e.g. via ACME, the same protocol Let’s Encrypt uses. step-ca can offer ACME.
  3. Firefox uses its own certificate store. The CA has to be added there as well (or via policy for all devices).

Part 3: why a CA is hard to undo (approx. 3 min)

  • After a short time, the root certificate is on every school device. Whoever rebuilds the CA has to re-equip every device and replace every certificate issued.
  • Whoever steals the CA’s private key can issue valid certificates for any name, even for bank.at, which the school devices will then trust. The key is the most valuable secret in the school network.
  • In practice you therefore build two tiers: a root CA that is almost always switched off (offline), and an issuing CA below it. The demo simplifies this to one tier.
  • The name, lifetime and key length of the CA cannot be changed afterwards. That is why a CA is planned and documented before it is installed, e.g. with an architecture decision record (ADR, see session 6).

Security and data protection

No legal advice

This section gives technical orientation. Legal questions (e.g. legal basis, retention periods, data processing agreements) are clarified by the school with the data protection officer and the school maintainer.

The essentials

TopicMeasure
Few administrator accountsA normal account for daily work, a separate administrator account for administration. The domain administrator is used only for domain tasks.
One service, one serverEach role on its own server or container: a fault in or attack on the web server does not immediately reach the domain controller. This is exactly how the lab is built.
Only necessary servicesWhat is not needed is not installed. Server Core and minimal Debian installations have a smaller attack surface.
UpdatesUpdate servers regularly, in the lab too. Debian: unattended-upgrades for security updates. Windows: Windows Update.
Remote accessNever Remote Desktop or SSH directly from the internet. SSH with keys, Remote Desktop with NLA, from outside only via VPN with multi-factor login.
Open resolvers and DHCPDNS answers recursive queries only from your own network. Only one planned DHCP server per network; rogue DHCP servers are blocked on the switch (DHCP snooping).
EncryptionWebsites only with HTTPS. Internal certificates from your own certificate authority instead of clicking browser warnings away. SMB1 stays switched off.
BackupDomain controllers, shares and configuration files are backed up, and restoring is practised. A snapshot is not a backup.

Data protection in the school context

  • Directory service: it contains names, class membership, login times and groups of minors. This belongs in the record of processing activities (see documentation script).
  • Logs: DHCP (which device was on the network when), DNS (which sites are visited), print server (who prints what) and remote access (who logs in when) generate personal logs. Decide who may see them and when they are deleted.
  • Own server or cloud: for roles in the cloud (Entra ID, Universal Print, Autopilot), the data is with a provider. That requires a data processing agreement and a check of where the data is processed. With your own servers, the school is responsible for operation and security itself.
  • Images (team 7): a disk image can contain data of the last person who used the reference machine. Never use the reference machine with real accounts. Wipe old disks securely before passing them on.
  • Test data: in the lab only made-up names (lehrer01, schueler01). No real class lists.
